# 고객 요청 대응 협업 플랫폼 설계

## 목적

현재의 BM25 기반 유사 사례 검색 프로토타입을 확장해, 고객 요청 담당자가 하나의 VOC 안에서 요청 라운드, 부서별 과제, 검토·승인, 고객 회신, 이력과 알림을 관리한다. 과거 완료 사례의 Top 3 검색은 그대로 유지하며, 검색 결과는 참고용으로만 제공하고 사용자가 최종 판단한다.

## 운영 환경

| 구분 | 외부 검토판 | 사내 운영판 |
| --- | --- | --- |
| 화면 | Vercel의 Next.js | 사내 Next.js |
| API | 공개 HTTPS FastAPI | 사내 FastAPI |
| 데이터 | Supabase PostgreSQL, 누적 보존 | 사내 PostgreSQL |
| 메일 | 미리보기·발송 이력만 | 회사 SMTP 또는 Outlook 실제 발송 |
| 번역 | 미리보기 또는 비활성화 | CPU 경량 번역 모델 |

동일 소스코드를 사용하며 환경 변수로 데이터베이스 연결, 실제 메일 발송, 번역 모델을 분리한다. 외부 검토판의 변경 데이터는 초기화하지 않고 보존한다. 학습용 135건과 사용자가 추가하는 테스트 15건이 누적되어 150건 이상이 되는지 검증 가능해야 한다.

## 접근 통제

- URL을 아는 사용자는 대시보드·아카이브·VOC 상세를 조회할 수 있다.
- 등록, 수정, 배정, 승인, 종결, 기준정보 관리, Excel/CSV 다운로드는 공용 비밀번호와 작성자명을 요구한다.
- 공용 비밀번호 값은 코드나 DB 평문이 아닌 환경 변수의 해시값으로만 관리한다.
- 5회 연속 실패하면 15분 동안 변경·다운로드를 제한한다.
- 모든 변경에는 작성자명, 시각, 변경 항목, 변경 전후 값을 감사 이력으로 남긴다.
- 일반 사용 화면은 물리 삭제를 제공하지 않는다. 삭제는 `deleted` 상태와 사유를 기록하고, 취소는 `cancelled` 상태와 고객 요청 취소 사유를 기록한다. 두 상태 모두 운영 집계와 Top 3 대상에서 제외한다.

## 핵심 데이터 모델

기존 `voc_cases`는 과거 아카이브와 Top 3 검색의 원천으로 유지한다. 협업 기능은 아래 테이블을 추가한다.

- `voc_requests`: VOC Case, 요청 라운드 번호, 고객 요청, 원문 메일, 발신자 이름·이메일·회사명, 번역 초안·확정 번역문, 유형·세부 유형, 제품·설비, 우선순위, 전체 단계, 취소/삭제 사유를 보관한다.
- `department_tasks`: 요청 라운드별 부서 과제. 담당자·직책자 이름/이메일, 상태(`not_started`, `reviewing`, `in_progress`, `completed`, `delayed`, `excluded`), 대응 내용, 완료 예정일, 지연 사유, ECM 링크를 보관한다.
- `task_reviews`: 부서 직책자 승인·반려와 고정 최종 승인자의 승인·반려를 보관한다. 반려 시 과제는 `reviewing`으로 돌아간다.
- `voc_stage_history`: 요청 접수 → 대응 중 → 부서별 검토 요청 → 직책자 검토 요청 → 고객 회신 → 완료 및 역방향 전환의 사유와 ECM 링크를 보관한다.
- `change_audits`: 인증된 모든 변경의 전후 JSON, 작성자, 시각을 보관한다.
- `notification_logs`: 발송 대상, 제목, 본문, 예정/발송 시각, 환경별 실제 발송 여부를 보관한다.
- `master_*`: 고객사, 제품·설비, VOC 유형·세부 유형, 부서·담당자·직책자, 고정 최종 승인자, 템플릿과 알림 시각을 관리한다.

## 업무 규칙

1. 고객 대응 담당자가 사내 메일 원문을 붙여 넣으면 규칙으로 발신자 이름·이메일·회사명만 추출한다. 회사명이 불명확하면 비워 두고 사용자가 확정한다. 유형·세부 유형·제품/설비·요청 내용은 사용자가 수정·확정한다.
2. 새 VOC에는 수정 불가한 `VOC-YYYY-NNNN` Case ID를 자동 발급한다. 임시 저장은 인증된 서버 저장으로 처리한다.
3. Top 3은 `closed` 사례만 대상으로 `customer_request + original_mail_body + full_response_history`를 BM25로 검색한다. Subtype이 정확히 일치하면 `BM25 × 1.1`을 사용한다.
4. 한 VOC에 여러 요청 라운드를 둔다. 고객 회신 뒤 추가 요청이 오면 같은 Case에 다음 라운드를 만들고 이전 부서 과제를 재개한다. 불필요 부서는 해당 라운드에서 `excluded` 처리한다.
5. 전체 단계와 부서 과제 상태는 분리한다. 모든 활성 부서 과제가 완료되어도 고객 대응 담당자가 승인하기 전에는 다음 전체 단계로 자동 전환하지 않는다.
6. 부서 과제 완료에는 진행 상태·대응 내용·완료 예정일이 필수다. 지연 사유와 ECM 링크는 선택이다. 기한을 넘기면 과제는 자동으로 `delayed`가 되고 지연 사유를 요구한다.
7. 고객 회신은 각 부서 직책자 승인 후, 모든 VOC에 고정된 최종 승인자/조직의 승인까지 끝난 경우에만 가능하다. 회신 초안은 한국어로 생성해 담당자가 확정한다.
8. 외국어 원문은 보존한다. 사내 운영판에서는 CPU 경량 번역 모델로 한국어 초안을 생성하고 사용자가 수정·확정한다. 한국어 원문은 번역본을 만들지 않는다.

## 알림 규칙

- 기본 처리 시각은 평일 09:00 Asia/Seoul이며 관리 도구에서 변경 가능하다.
- 높은 우선순위: 부서 배정 즉시와 기한 전 매일, 부서 담당자·부서 직책자·최종 승인자 모두에게 알린다.
- 일반 우선순위: D-2, D-1, 기한 초과 매일, 부서 담당자와 부서 직책자에게 알린다.
- 요청 라운드 재개 시 해당 과제 담당자와 직책자에게 즉시 알린다.
- 사내 운영판에서만 실제 메일을 보낸다. 외부 검토판은 같은 내용을 `notification_logs`에 미리보기로 기록한다.
- 제목/본문 템플릿은 VOC 번호, 고객사, 제품/설비, 요청 제목, 현재 단계, 담당 부서, 기한, ECM 링크 변수를 지원한다.

## 화면

- 대시보드: 단계별 VOC 현황, 마감 임박/지연 부서 과제, 최근 고객 요청을 동일 비중으로 표시한다. 기본 최근 30일, 이번 주·이번 달·사용자 지정 기간 필터를 둔다.
- 새 요청 등록: 메일 붙여넣기, 자동 추출 확인, 기준정보 선택, 임시 저장, Top 3, 부서 배정을 제공한다.
- 고객 대응 관리: 요청 라운드, 전체 단계, 부서별 과제, 승인/반려, 고객 회신 초안, 변경 이력을 제공한다.
- 고객 대응 아카이브: 고객사·제품/설비·유형·날짜·상태 필터, 최신 접수일 정렬, 상세, 인증된 CSV/XLSX 다운로드를 제공한다.
- 알림: 예정/발송 이력과 템플릿 미리보기를 제공한다.
- 관리 도구: 기준정보·고정 최종 승인자·알림 시각·템플릿을 인증 후 관리한다.

## 비범위 및 안전 경계

- 로그인 계정·개인별 권한 체계는 구현하지 않는다. 변경용 공용 비밀번호와 작성자명만 사용한다.
- ECM 파일 업로드는 구현하지 않고 링크와 메타데이터만 저장한다.
- Sentence Transformer는 기획상 비교안일 뿐 런타임 구현하지 않는다.
- 실제 SMTP/Outlook 자격 증명, 외부 FastAPI 호스팅 계정, Vercel/Supabase 토큰은 코드에 포함하지 않는다. 배포 시 환경 변수로만 주입한다.
